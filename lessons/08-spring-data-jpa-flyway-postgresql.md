# Lesson 08 — Spring Data JPA + Flyway + PostgreSQL

**Date:** 2026-08-11 · **Phase:** 4 (Data) · **Prereq:** Lesson 07 (Security — the `@Transactional` proxy you'll now use for real)

> **All code in this lesson is verified.** Compiled (Hibernate 7.4.1 via Boot 4.1.0) and run against PostgreSQL 17.10 in Docker — 8 curl probes passed, including the N+1 fix.

## 1. The mental model that changes everything

You know ORMs from NestJS: TypeORM/Prisma map tables to objects, repositories abstract queries. Spring Data JPA is the same idea — but three things work differently under the hood, and they explain most "JPA is magic/broken" complaints:

**1. The repository interface IS the implementation.** You declare `findByShortCode(...)` and Spring Data *generates* the SQL from the method name at startup. No `@Injectable()`, no `TypeOrmModule.forFeature` — the interface itself is the bean. (Compare: Prisma generates a client; Spring Data generates the *repository* from your method names.)

**2. Entities are mutable classes, never records.** Records are `final` → Hibernate can't proxy them for lazy loading (the Lesson 05/07 nuance becomes concrete). An entity needs: a no-arg constructor (protected is fine), mutable fields, and getters. **DTOs stay records; entities are classes.** This split is the architecture.

**3. The transaction IS the session.** Hibernate's persistence context (the cache of managed entities) lives inside a transaction. Access a lazy relation *outside* a transaction → `LazyInitializationException`. This is why `@Transactional` is not optional decoration — it's the *session boundary*.

## 2. The syntax delta: TypeORM/Prisma → JPA

| TypeORM / Prisma (known) | Spring Data JPA (learning) |
|---|---|
| `@Entity()` class | `@Entity` class + `@Table(name = "urls")` |
| `@PrimaryGeneratedColumn()` | `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` |
| `@Column({ name: 'short_code' })` | `@Column(name = "short_code", nullable = false, unique = true)` |
| `@ManyToOne(() => User)` | `@ManyToOne(fetch = FetchType.LAZY)` + `@JoinColumn(name = "owner_id")` |
| `@OneToMany(() => Url)` | `@OneToMany(mappedBy = "owner")` |
| repository class with methods | `interface UrlRepository extends JpaRepository<UrlEntity, Long>` |
| `repo.findOneBy({ code })` | `repo.findByShortCode(code)` → returns `Optional` |
| migrations (Prisma migrate / TypeORM) | **Flyway** — plain SQL files, versioned |
| `LEFT JOIN` + relations | lazy loading + `JOIN FETCH` / `@EntityGraph` |

**Key differences that bite:**
- **`@ManyToOne` is EAGER by default** (the opposite of `@OneToMany`!). Always set `FetchType.LAZY` explicitly — eager `ManyToOne` is the classic N+1 generator.
- **Repository methods return `Optional`** for single results — the Lesson 02 `Optional` discipline lands here.
- **Migrations are plain SQL**, not generated from entities. The DB schema is *yours*; Hibernate validates it against the entities at boot (fail fast — Lesson 05's philosophy).

## 3. Flyway — versioned SQL migrations

**Why Flyway instead of `ddl-auto: update`?** `update` lets Hibernate alter the schema from entities — fine for prototypes, but in production the schema is *shared state*: two developers' entity changes collide, and there's no history, no rollback path. Flyway makes the schema **code**: versioned SQL files applied exactly once, recorded in `flyway_schema_history`.

**Boot 4 gotcha (verified):** the dependency is NOT `flyway-core` — Boot 4 split auto-configuration into modules, so you need the starter **plus** the PostgreSQL support module (Flyway 10+ made DB support separate):

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

With only `flyway-core` (the old way), the app starts **without running migrations at all** — Hibernate validation then fails with `missing table [urls]`. With the starter but no postgres module: `Unsupported Database: PostgreSQL 17.10`. Both errors are silent-ish and confusing — now you know what they mean.

**`src/main/resources/db/migration/V1__init.sql`** — naming convention `V<version>__<description>.sql`:

```sql
-- V1: initial schema for the URL shortener
CREATE TABLE users (
    id            BIGSERIAL PRIMARY KEY,
    username      VARCHAR(32)  NOT NULL UNIQUE,
    password_hash VARCHAR(100) NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE urls (
    id           BIGSERIAL PRIMARY KEY,
    short_code   VARCHAR(16) NOT NULL UNIQUE,
    original_url TEXT        NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    owner_id     BIGINT      NOT NULL REFERENCES users (id)
);

CREATE INDEX idx_urls_owner ON urls (owner_id);
```

- `BIGSERIAL` → `BIGINT GENERATED BY DEFAULT AS IDENTITY` — Postgres auto-increment.
- `TIMESTAMPTZ` — stores UTC; the driver tz fix below matters for this.
- **Never edit an applied migration.** Add `V2__...sql` instead. Flyway checksums applied files and refuses to boot on mismatch (fail fast again).

## 4. The entities — mutable classes, explicit mappings

**`domain/UserEntity.java`:**

```java
package com.icd.urlshortener.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.time.Instant;

@Entity
@Table(name = "users")
public class UserEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 32)
    private String username;

    @Column(name = "password_hash", nullable = false, length = 100)
    private String passwordHash;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    protected UserEntity() { } // JPA needs a no-arg constructor

    public UserEntity(String username, String passwordHash) {
        this.username = username;
        this.passwordHash = passwordHash;
        this.createdAt = Instant.now();
    }

    public Long getId() { return id; }
    public String getUsername() { return username; }
    public String getPasswordHash() { return passwordHash; }
    public Instant getCreatedAt() { return createdAt; }
}
```

- `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` — the DB generates ids (like `SERIAL`).
- `@Column(nullable = false, unique = true)` — **maps to DDL constraints**; Hibernate validates these against the Flyway schema at boot.
- `updatable = false` — `created_at` is write-once; Hibernate will never include it in UPDATE statements.
- Protected no-arg constructor — Hibernate instantiates entities via reflection; your public constructor is for *your* code.
- **No setters needed** — Hibernate mutates fields reflectively. Immutable-on-the-outside entity.

**`domain/UrlEntity.java`** — the relation:

```java
package com.icd.urlshortener.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import java.time.Instant;

@Entity
@Table(name = "urls")
public class UrlEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "short_code", nullable = false, unique = true, length = 16)
    private String shortCode;

    @Column(name = "original_url", nullable = false)
    private String originalUrl;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    // ManyToOne defaults to EAGER in JPA (the opposite of OneToMany) — always set LAZY explicitly
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "owner_id", nullable = false)
    private UserEntity owner;

    protected UrlEntity() { }

    public UrlEntity(String shortCode, String originalUrl, UserEntity owner) {
        this.shortCode = shortCode;
        this.originalUrl = originalUrl;
        this.owner = owner;
        this.createdAt = Instant.now();
    }

    public Long getId() { return id; }
    public String getShortCode() { return shortCode; }
    public String getOriginalUrl() { return originalUrl; }
    public Instant getCreatedAt() { return createdAt; }
    public UserEntity getOwner() { return owner; }
}
```

- `@ManyToOne` + `@JoinColumn(name = "owner_id")` — the FK column, matching the migration.
- `FetchType.LAZY` — the `owner` is a **proxy** until accessed *inside a transaction*. The proxy is what records can't do (Lesson 07's CGLIB discussion).

## 5. The repositories — interfaces that become beans

**`domain/UrlRepository.java`:**

```java
package com.icd.urlshortener.domain;

import java.util.List;
import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;

public interface UrlRepository extends JpaRepository<UrlEntity, Long> {

    Optional<UrlEntity> findByShortCode(String shortCode);

    // FIX for N+1: one query with JOIN FETCH — owner arrives in the same result set
    @Query("select u from UrlEntity u join fetch u.owner")
    List<UrlEntity> findAllWithOwner();
}
```

**`domain/UserRepository.java`:**

```java
package com.icd.urlshortener.domain;

import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;

public interface UserRepository extends JpaRepository<UserEntity, Long> {

    Optional<UserEntity> findByUsername(String username);
}
```

- **Derived queries:** `findByShortCode` → `SELECT ... WHERE short_code = ?`. Spring Data parses the method name. `Optional` return type = no result → empty Optional (no null, Lesson 02).
- **`@Query`** — hand-written JPQL (entity language, not SQL — `u.owner` is the field, not the table). `join fetch` is the N+1 fix.

### The N+1 problem — why `findAllWithOwner` exists

```java
// BAD — N+1: 1 query for urls + 1 query PER url for its owner
urlRepository.findAll().stream()
    .map(u -> u.getOwner().getUsername())   // lazy owner → Hibernate fires a query per row
```

With 100 urls: **101 queries**. The fix, in order of preference:

1. **`JOIN FETCH` in JPQL** (`findAllWithOwner`) — one query, owner loaded in the same result set. ✅ what we use.
2. `@EntityGraph(attributePaths = "owner")` on a derived query — same effect, no JPQL.
3. `@BatchSize(size = 50)` on the relation — loads 50 owners per query (mitigation, not cure).
4. Eager fetching — the trap: it silently applies to *every* query.

**How to see it (do this in the exercise):** enable `spring.jpa.show-sql: true` and watch the console. N+1 shows as a burst of identical `select ... from users` statements; the fix shows one query with `left join`.

## 6. The service — `@Transactional` becomes real

**`shortener/UrlShortenerService.java`** — replaces the `ConcurrentHashMap` store from Lesson 06:

```java
package com.icd.urlshortener.shortener;

import com.icd.urlshortener.domain.UrlEntity;
import com.icd.urlshortener.domain.UrlRepository;
import com.icd.urlshortener.domain.UserEntity;
import com.icd.urlshortener.domain.UserRepository;
import java.util.List;
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class UrlShortenerService {

    private final IdGenerator idGenerator;
    private final UrlRepository urlRepository;
    private final UserRepository userRepository;

    public UrlShortenerService(IdGenerator idGenerator,
                               UrlRepository urlRepository,
                               UserRepository userRepository) {
        this.idGenerator = idGenerator;
        this.urlRepository = urlRepository;
        this.userRepository = userRepository;
    }

    @Transactional
    public String create(String originalUrl, String username) {
        UserEntity owner = userRepository.findByUsername(username)
            .orElseThrow(() -> new IllegalStateException("user not found: " + username));
        String code = idGenerator.nextId();
        urlRepository.save(new UrlEntity(code, originalUrl, owner));
        return code;
    }

    @Transactional(readOnly = true)
    public Optional<String> resolve(String code) {
        return urlRepository.findByShortCode(code)
            .map(UrlEntity::getOriginalUrl);
    }

    // N+1 FIXED: findAllWithOwner() uses JOIN FETCH — one query total
    @Transactional(readOnly = true)
    public List<UrlStats> listStats() {
        return urlRepository.findAllWithOwner().stream()
            .map(u -> new UrlStats(u.getShortCode(), u.getOriginalUrl(), u.getOwner().getUsername()))
            .toList();
    }

    public record UrlStats(String shortCode, String originalUrl, String owner) { }
}
```

- **`@Transactional` is now load-bearing** (Lesson 07's proxy!): without it, `create()`'s lazy `owner` access and the session lifecycle break. The proxy opens the transaction, Hibernate opens the session, the entities become managed.
- **`readOnly = true`** on reads — a real optimization hint (no dirty checking, and the DB can use a read-only snapshot).
- **Never put `@Transactional` in controllers** — the transaction belongs to the service boundary.
- `save()` on a new entity → `INSERT`; on a managed entity → `UPDATE` at flush. You don't call `update()` — the persistence context tracks changes (this is the "magic" — dirty checking at commit).

## 7. The web layer — auth now persists

**`AuthController`** — `UserStore` (Lesson 07's ConcurrentHashMap) is deleted; registration writes to PostgreSQL:

```java
@PostMapping("/register")
@ResponseStatus(HttpStatus.CREATED)
public AuthResponse register(@Valid @RequestBody RegisterRequest request) {
    userRepository.save(new UserEntity(request.username(), passwordEncoder.encode(request.password())));
    return new AuthResponse(jwtService.issue(request.username()), request.username());
}

@PostMapping("/login")
public AuthResponse login(@Valid @RequestBody LoginRequest request) {
    UserEntity user = userRepository.findByUsername(request.username())
        .orElseThrow(InvalidCredentialsException::new);
    if (!passwordEncoder.matches(request.password(), user.getPasswordHash())) {
        throw new InvalidCredentialsException();
    }
    return new AuthResponse(jwtService.issue(user.getUsername()), user.getUsername());
}
```

**`UrlController.create`** now knows *who* is calling — the JWT filter (Lesson 07) put the username in the `SecurityContext`:

```java
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public UrlResponse create(@Valid @RequestBody CreateUrlRequest request) {
    // who is calling? the JWT filter put the username in the SecurityContext (Lesson 07)
    String username = SecurityContextHolder.getContext().getAuthentication().getName();
    String id = urlShortenerService.create(request.originalUrl(), username);
    return new UrlResponse(id, request.originalUrl(), "/" + id);
}
```

Plus a stats endpoint that exercises the N+1 fix:

```java
@GetMapping
public List<UrlShortenerService.UrlStats> stats() {
    return urlShortenerService.listStats();
}
```

## 8. `application.yml` — the three gotchas that WILL bite you

```yaml
spring:
  datasource:
    # TimeZone=UTC in the URL: the JVM's own tz (Asia/Saigon) is sent in the JDBC
    # startup packet and the Debian postgres image lacks that tzdata entry.
    # Explicit UTC = deterministic, and UTC is what we store anyway.
    url: jdbc:postgresql://localhost:55432/urlshortener?TimeZone=UTC
    username: urlshortener
    password: urlshortener
  jpa:
    hibernate:
      ddl-auto: validate        # schema comes from Flyway; Hibernate only validates
    open-in-view: false         # the OSIV trap — see below
    properties:
      hibernate:
        jdbc:
          time_zone: UTC        # store UTC; the app converts — avoids JVM-vs-DB tz mismatch
  flyway:
    enabled: true
```

**Gotcha 1 — the port.** `localhost:5432` is *not* guaranteed to be your container. This machine has a **native Windows PostgreSQL service** squatting on 5432 (and other projects use 5433/6432). The lesson's container maps host **55432** → container 5432. Symptom of hitting the wrong server: `FATAL: password authentication failed` — your credentials are right, but they're for a different Postgres. Always check `netstat -ano | grep :5432` and `docker port <container>`.

**Gotcha 2 — the timezone.** The JVM sends its default timezone (`Asia/Saigon`) in the JDBC startup packet — *before* any `hibernate.jdbc.time_zone` property can apply. The slim Debian postgres image rejects it: `FATAL: invalid value for parameter "TimeZone": "Asia/Saigon"`. Fixes (both used):
- URL: `?TimeZone=UTC` — documented, deterministic.
- Run the JVM with `-Duser.timezone=UTC` (the URL param alone was NOT enough in testing — the driver still sent the JVM default; verified with jshell + raw JDBC).

**Gotcha 3 — `open-in-view: false`.** Spring Boot's default (`true`) keeps the Hibernate session open for the whole HTTP request — so lazy loading works in controllers *by accident*, at the cost of holding DB connections open and hiding transaction boundaries. Turn it off (as above) and lazy access outside a service transaction fails loudly with `LazyInitializationException` — the correct failure. This is a top "what would you change in a legacy codebase" interview answer.
